# 网络游戏在线人数监控设计

文档状态：设计方案

## 一、目标与范围

在 PrismPanel 中增加网易网络游戏在线人数监控能力：

- 面板级共用一个网易账号；
- 超级管理员负责网易账号验证、保存和删除；
- 保存所有采集到的网络游戏基础信息；
- 每 15 分钟至 60 分钟采集一次在线人数，默认 15 分钟；
- 每次请求 20 个游戏，持续请求到最后一页；
- 所有在线人数大于 0 的采样写入数据库；
- 总览页按最近一次成功采集结果展示指定数量的游戏折线；
- 支持强制显示指定游戏 ID；
- 支持最近 24 小时到最早保留记录的时间范围；
- 支持超级管理员手动立即采集；
- 每天刷新一次游戏详情数据。

本功能不在前端直接请求网易接口，网易账号密码和网易会话令牌不暴露给浏览器。

## 二、现有代码与改造边界

`网络游戏列表获取/main.py` 已实现网易 MPay 登录、X19 OTP 认证、请求签名和分页列表请求，可作为协议移植到 Go 的参考实现。该脚本当前是一次性命令行工具，账号写在源码常量中，分页参数也不是本需求的最终配置，因此不能直接作为面板后台任务运行。

面板现有能力可以复用：

- `panel/internal/secret` 生成和加载面板主密钥；
- 节点服务中的 AES-GCM 加密存储模式；
- MySQL 初始化表结构和统一 API 响应格式；
- Vue 3、Element Plus、Lucide 图标和现有 SVG 折线图组件。

现有 `panel/internal/metrics` 是内存指标，只有约 10 分钟保留期，不能用于本功能的长期历史；网络游戏数据需要单独持久化。

## 三、总体架构

```text
Vue 设置页/总览页
        |
        v
面板 REST API
        |
        +-- 网易账号服务
        |     +-- 加密凭据存储
        |     +-- 网易协议客户端
        |     +-- 登录会话（内存/Redis 短期缓存）
        |
        +-- 网络游戏采集器
        |     +-- 定时任务
        |     +-- 分页列表请求
        |     +-- 采集批次状态
        |     +-- 在线人数入库
        |
        +-- 游戏目录与历史查询
              +-- MySQL 基础信息
              +-- MySQL 在线人数历史
```

建议将 Python 协议实现移植为 Go 服务。这样面板发布包不依赖 Python 运行时，后台任务、凭据解密和 API 可以共享同一套生命周期和错误处理。

## 四、数据存储方案

### 4.1 MySQL 与 Redis 的职责

MySQL 是唯一的持久化数据源，保存可恢复、可查询的业务数据。Redis 只保存短期运行状态：

| 数据 | MySQL | Redis |
|---|---:|---:|
| 网易账号密文、设备缓存 | 是 | 否 |
| 游戏基础信息 | 是 | 否 |
| 在线人数历史 | 是 | 否 |
| 采集批次和错误记录 | 是 | 否 |
| 面板/监控设置 | 是 | 否 |
| 网易短期会话令牌 | 可选 | 推荐 |
| 最新采集结果缓存 | 可选 | 推荐 |
| 多实例采集锁 | 否 | 推荐 |
| 实时状态通知 | 否 | 推荐 |

单实例部署时，采集器可以由面板进程内的 Go goroutine 运行；Redis 锁仍应预留，以避免将来多面板实例重复采集。Redis 丢失不能导致历史数据丢失，缓存失效后应回源 MySQL。

### 4.2 游戏基础信息表

建议表名：`net_games`。

字段：

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `game_id` | `VARCHAR(64)` | 网易游戏 ID，主键 |
| `name` | `VARCHAR(255)` | 最近一次列表名称 |
| `summary` | `TEXT` | 列表摘要 |
| `author` | `VARCHAR(255)` | 作者/开发者 |
| `versions` | `JSON` | Minecraft 版本列表 |
| `ip` | `VARCHAR(255)` | 服务器 IP/主机 |
| `port` | `INT` | 服务器端口 |
| `address` | `VARCHAR(512)` | 展示地址 |
| `publish_time` | `BIGINT` 或 `DATETIME` | 网易返回的发布时间，需保留原始语义 |
| `images` | `JSON` | 图片 URL 列表 |
| `description` | `MEDIUMTEXT` | 详情 HTML/文本 |
| `first_seen_at` | `DATETIME(6)` | 首次发现时间 |
| `last_seen_at` | `DATETIME(6)` | 最近在列表出现时间 |
| `details_updated_at` | `DATETIME(6)` | 最近一次详情刷新时间 |
| `updated_at` | `DATETIME(6)` | 记录更新时间 |

列表接口每次返回的 `name`、`summary`、`last_seen_at` 应及时更新。详情字段不需要每 15 分钟重复请求。

### 4.3 在线人数历史表

建议表名：`net_game_online_samples`。

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `game_id` | `VARCHAR(64)` | 关联 `net_games.game_id` |
| `online_count` | `INT UNSIGNED` | 在线人数，只写入大于 0 的值 |
| `sampled_at` | `DATETIME(6)` | 采样时间，统一使用 UTC |
| `run_id` | `CHAR(32)` | 对应采集批次，可选但建议保留 |

建议使用 `(game_id, sampled_at)` 唯一键或索引，并增加 `(sampled_at, game_id)` 索引支持按时间清理和批量查询。

0 人不写入该表。查询图表时，若某次采集批次成功返回了该游戏但没有对应正数采样，则将该点补为 0；如果该批次失败或没有返回该游戏，则不生成点。

### 4.4 采集批次表

为了区分“确实为 0 人”和“采集失败”，建议增加：

`net_game_collection_runs`：

| 字段 | 说明 |
|---|---|
| `run_id` | 批次 ID，主键 |
| `started_at` | 开始时间 |
| `finished_at` | 结束时间 |
| `status` | `running/success/failed` |
| `total_games` | 本次列表返回总数 |
| `error_code` | 失败错误码 |
| `error_message` | 脱敏后的错误信息 |

`net_game_collection_run_games`：

| 字段 | 说明 |
|---|---|
| `run_id` | 采集批次 |
| `game_id` | 游戏 ID |
| `observed` | 本批次是否在列表中成功观察到 |
| `online_count` | 本批次人数，可为 0 |

如果不希望额外保存每批次全部游戏，也至少要保存批次成功状态和本批次返回的游戏 ID 集合，否则前端无法严格判断 0 人与缺失的区别。

### 4.5 设置与凭据

建议增加面板设置表和凭据表：

`panel_settings` 保存全局设置，例如：

- `collection_interval_minutes`：15 至 60，默认 15；
- `history_retention_days`：默认 30；
- `display_game_count`：总览显示数量 N；
- `forced_game_ids`：强制 ID 列表；
- 默认图表时间范围等全局偏好。

`panel_credentials` 保存网易账号密文：

- 账号邮箱；
- AES-GCM 密文；
- nonce；
- 加密版本；
- 验证状态、最后验证时间；
- 创建和更新时间。

密码和设备缓存均使用现有面板主密钥加密。数据库和日志禁止保存明文密码、设备 key、网易 user token 或 session token。

## 五、网易账号与认证

### 5.1 权限

当前权限规则：

- 超级管理员：查看、验证、修改、删除网易账号；修改面板级采集设置；手动立即采集；查看采集错误状态。
- 普通管理员：不能查看或修改网易账号；可以按现有面板权限使用允许的业务能力。面板级设置是否可修改由后续更细粒度权限控制；当前非管理员不可修改面板级设置。
- 其他用户：不能修改面板级设置，只能读取其被授权的总览和历史数据。

网易账号 API 必须在服务端再次检查权限，不能只依赖前端隐藏按钮。账号读取接口只返回脱敏邮箱和状态，不返回密码。

### 5.2 保存与验证流程

1. 超级管理员输入邮箱和密码。
2. 面板在内存中创建网易客户端并执行完整登录验证。
3. 验证成功后，加密保存邮箱、密码和设备缓存。
4. 立即触发一次网络游戏采集。
5. 验证失败时不覆盖旧凭据，并返回明确错误。

网易返回安全验证地址、短信/实名要求、限流或服务端错误时，应分别返回对应状态；只有明确的账号认证失败才提示账号或密码错误。

短期网易会话令牌只放内存或 Redis，并设置过期时间。面板重启后重新登录，不直接依赖持久化的短期 token。

## 六、采集调度与分页

### 6.1 周期采集

- 保存账号后立即执行一次；
- 默认每 15 分钟执行一次；
- 可配置范围 15 到 60 分钟，后端强制校验；
- 面板启动后，如果已有有效账号，按上次成功采集时间决定是否立即补采；
- 同一时间只允许一个采集任务执行；
- 支持设置页中的“立即采集”按钮；
- 采集成功和失败都写入批次记录。

Redis 部署下使用带 TTL 的分布式锁，例如 `prism:net-games:collector-lock`，TTL 必须小于任务最大执行时长并支持续租。单实例模式也要保留进程内互斥，避免手动采集和定时采集并发运行。

### 6.2 列表请求

每次请求参数固定使用：

- `length=20`；
- `offset=0,20,40...`；
- 持续请求直到返回空数组或返回数量小于 20；
- 增加最大页数/最大总量保护，避免接口异常时无限循环。

每个实体至少解析：

- `entity_id` -> `game_id`；
- `name`；
- `brief_summary` -> `summary`；
- `online_count`。

本轮采集列表阶段不强制对每个游戏请求详情接口，避免每 15 分钟产生大量额外请求。

### 6.3 在线人数入库

一次批次中：

1. 创建 `running` 批次；
2. 分页获取全部列表；
3. 更新或插入 `net_games` 的列表字段；
4. 记录本批次所有观察到的游戏及人数；
5. 仅对 `online_count > 0` 的游戏插入在线人数历史；
6. 事务提交基础信息、批次明细和正数采样；
7. 标记批次为 `success`。

中途失败时批次标记为 `failed`，不把部分结果当作完整采集结果参与当前显示排名。必要的基础信息可以在独立事务中保存，但不能改变“最近一次成功采集”语义。

## 七、游戏详情刷新

详情字段需要保存：`author`、`versions`、`ip`、`port`、`address`、`publish_time`、`images`、`description`。

建议策略：

- 新游戏首次出现时获取详情；
- 详情缺失时补获取；
- 每天后台刷新一次已知游戏详情；
- 用户打开详情页时，如果详情过期，可提供手动刷新或后台刷新；
- 详情请求失败不影响当前在线人数采集，保留旧详情并记录错误状态。

每天刷新任务应有并发和速率限制，避免一次性对大量游戏发起详情请求。详情字段来自列表或详情接口时按字段级别更新，不能因为详情接口失败而清空已有内容。

如果强制 ID 在当前成功列表中不存在，仍可保留其配置；总览显示 0 人，名称、作者等缺失字段显示“未知”。如果该 ID 在本次采集过程中因批次失败而没有被成功观察，则本周期不计入最终显示数量。

## 八、总览显示选择算法

配置 `N=10`、强制 ID 为 `[A,B,C,D]` 时：

1. 读取最近一次成功采集批次；
2. 在该批次中找到仍然有效的强制 ID；
3. 强制 ID 去重后先占用名额；
4. 按最近一次成功采集的 `online_count` 降序选择其他游戏；
5. 选取数量为 `N - 有效强制 ID 数量`；
6. 强制 ID 采集失败或未被成功观察时，不占用名额；
7. 最终数量不足 N 时，按实际可用游戏数量返回，不伪造数据。

因此，10 个名额、4 个强制 ID、其中 1 个本周期采集失败时，会使用 3 个有效强制 ID，再从其余游戏中选择前 7 个。

如果游戏在成功批次中出现但人数为 0，它仍然可以作为强制项显示；没有正数历史采样时，图表对应点按批次信息补为 0。

## 九、颜色与图例

图表右上角显示图例，图例包含颜色、游戏名称和当前在线人数。

颜色采用固定的排名色板：

- 当前在线人数排名第 1 的游戏使用红色；
- 之后按橙、黄、绿、蓝等预设顺序分配；
- 颜色按当前排名重新分配，而不是永久绑定游戏 ID；
- 当人数排名变化时，同一游戏的颜色可能变化，这是“人数最多始终使用红色”的直接结果；
- 游戏数量超过色板时循环使用或使用补充色，但应尽量避免同一视图内颜色重复。

图例颜色分配必须由后端返回最终排序后的游戏顺序，或由前端基于同一排序算法生成，避免前后端颜色不一致。建议由后端返回 `rank`，前端只负责映射色板。

## 十、历史查询与图表交互

默认查询最近 24 小时。前端按住 Shift 滚动鼠标滚轮调整 X 轴时间范围：

- 向上滚动缩小时间范围；
- 向下滚动扩大时间范围；
- 最小范围不小于一个采集间隔；
- 最大范围不超过当前保留数据的最早时间；
- 时间范围变化后重新请求或在已加载数据中筛选；
- 采集失败造成的时间段显示为空白，不画成 0；
- 对于成功观察到但人数为 0 的游戏，绘制 0 点；
- 没有任何成功观察记录的游戏不绘制折线。

建议 API 返回统一的时间序列结构：

```json
{
  "game_id": "123",
  "name": "示例服务器",
  "rank": 1,
  "color_rank": 1,
  "latest_online_count": 120,
  "points": [
    {"sampled_at": "2026-07-19T08:00:00Z", "value": 120},
    {"sampled_at": "2026-07-19T08:15:00Z", "value": 0}
  ]
}
```

基础信息详情接口单独返回完整字段，避免总览图表接口携带大量图片和描述内容。

## 十一、建议 API

```text
GET   /api/v1/net-games/settings
PUT   /api/v1/net-games/settings

GET   /api/v1/net-games/account
POST  /api/v1/net-games/account/verify
DELETE /api/v1/net-games/account

POST  /api/v1/net-games/collect
GET   /api/v1/net-games/collector-status
GET   /api/v1/net-games/series
GET   /api/v1/net-games/{game_id}
POST  /api/v1/net-games/{game_id}/refresh-details
```

建议继续使用当前 `{success,data,error,request_id}` 响应格式。账号、设置、立即采集和详情刷新接口必须有服务端权限检查，并写入审计日志。

## 十二、历史清理

历史保留天数默认 30 天，由面板级设置控制。定时清理任务删除：

- 超过保留期限的 `net_game_online_samples`；
- 超过保留期限且不再需要审计的采集批次明细；
- 可以保留游戏基础信息，即使该游戏已经不再出现在网易列表中。

修改保留天数后应在下一次清理任务生效，设置保存本身不应阻塞。

## 十三、失败、重试与可观测性

- 登录失败：批次不执行，状态页显示账号验证失败；
- 需要安全验证：保存验证地址和脱敏提示，不自动绕过；
- 网络超时：按有限次数退避重试，仍失败则批次失败；
- 网易接口协议错误：记录错误码和请求 ID，避免把所有错误提示为密码错误；
- 详情失败：不影响在线人数采集，保留旧详情；
- 采集失败：不更新“最近成功采集”指针，不改变当前总览排名；
- 面板重启：恢复设置和历史数据，重新建立网易会话；
- Redis 不可用：单实例可以退化为进程内锁，多实例部署应将采集任务标记为不可安全执行；
- 所有密码、token、设备 key 和加密明文禁止进入日志、错误响应和审计详情。

设置页应显示：最近一次成功采集、最近一次失败、下次计划时间、当前账号验证状态和历史数据最早时间。

## 十四、实施顺序

1. 将 Python 协议行为整理为 Go 客户端，并用固定响应样本验证加密、签名和 JSON 解析。
2. 增加 MySQL 表、主密钥加密凭据服务和权限检查。
3. 实现网易账号验证、保存、删除和立即采集 API。
4. 实现分页采集器、采集批次、在线人数入库和历史清理。
5. 实现每日详情刷新任务。
6. 实现面板/监控设置和调度状态 API。
7. 在前端右上角增加设置入口，完成账号、面板设置和监控设置界面。
8. 扩展总览图表，加入多折线、图例、24 小时默认范围和 Shift+滚轮缩放。
9. 增加权限、并发采集、分页边界、0 人补点、失败批次、历史清理和图表查询测试。

## 十五、验收标准

1. 只有超级管理员可以读取、验证、修改和删除网易账号。
2. 密码不会出现在浏览器存储、API 响应、数据库明文和日志中。
3. 保存账号成功后立即采集一次，默认每 15 分钟执行，配置范围严格限制在 15 至 60 分钟。
4. 列表请求每页固定 20 个，并且能够自动停止在最后一页。
5. 所有游戏基础字段可以独立查看，详情刷新失败不会清空旧数据。
6. 所有游戏都参与保存；在线人数为 0 时不写入正数历史表。
7. 成功批次中的 0 人游戏在图表中显示 0，失败批次和未观察到的游戏显示为空白或跳过。
