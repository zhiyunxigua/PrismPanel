# PrismPanel 仓库（Repository）改造规划

> 状态：规划草案，待确认后实施
> 目标：将现有"插件仓库"升级为通用**仓库**——支持 7 大平台、通用内容包（zip 结构映射服务端目录）、完全配置与单独配置两种部署形态。

---

## 一、现状理解（基于现有代码）

### 1.1 现有插件仓库模型（panel/internal/plugins/）

- **按平台分目录**：`repositoryTypes = [spigot, velocity, bungee, fabric, forge]`（5 个）
- **制品结构**：每个插件 = `typeRoot/<pluginID>/`，含 `index.yaml` + 多版本 artifact（`<artifactID>/plugin.jar` + `config/` + `manifest.yaml`）
- **配置模型（关键限制）**：上传时可附带一个配置 zip，解压到"**插件配置目录**"（`config/`，语义 = Bukkit 插件的 `plugins/<name>/`）；manifest 记录 `ConfigSnapshot{Directory, Present, SHA256, Files, Size}`
- **部署**：
  - plugin bundle：jar → `<workspace>/plugins/`（Bukkit）或 `<workspace>/mods/`（Fabric/Forge）
  - config bundle：内容 → `<workspace>/plugins/<configDirectory>/`（**硬编码 plugins 目录**）
  - **mod 平台 config 部署被明确拒绝**（"use config sync instead"）
- **前端**：PluginsView.vue 有「插件仓库 / Mod 仓库」标签页、平台筛选、上传/部署/启停

### 1.2 现有能力的边界

| 项 | 现状 | 与需求的差距 |
|---|---|---|
| 平台 | 5（spigot/velocity/bungee/fabric/forge） | 缺 **neoforge**、**paper**（paper 目前并入 spigot） |
| 配置包 | 仅"插件配置目录"（plugins/<name>/） | 需**通用内容包**：zip 结构 = 服务端目录结构（config/→config/，其他→对应位置） |
| mod 平台配置 | 拒绝（走 config-sync） | 需支持 mod 服内容包部署 |
| 部署形态 | jar 与配置分离 | 需**完全配置**（mod+config+地图等整包同时部署） |

## 二、目标模型（用户需求）

### 2.1 命名与平台

- 「插件仓库」→ **「仓库」**（Repository），统一承载插件与 mod
- 平台分页（7）：**fabric / forge / neoforge / spigot / paper / velocity / bungee**
  - 新增 `neoforge`（NeoForge 加载器，mods.toml 解析与 forge 同源但 loader 不同）
  - 新增 `paper` 独立（与 spigot 同为 Bukkit API，部署目录仍 `plugins/`，仅平台标识与描述符解析独立）

### 2.2 制品 = jar（插件/mod）+ 内容包（Content Bundle）

上传 jar 时可**附加一个内容包 zip**，并选择类型：

| 类型 | 语义 | 部署目标 |
|---|---|---|
| **单独配置**（config bundle） | zip 内 `config/` 文件夹 → 服务端 `config/`；**zip 内其他文件/文件夹按结构映射到服务端对应位置**（"压缩包里有什么文件/文件夹，就上传对应位置"） | 解压到工作目录（相对结构） |
| **完全配置**（full bundle） | 整个 zip 即**服务端目录内容**（含 mods/jar、config、world 地图、plugins 等），一次部署 | 解压到工作目录（可含 world 等大目录） |

> 内容包与 jar 的关系：**单独配置** = 配置独立部署（jar 与配置分开推）；**完全配置** = jar 已包含在 zip 内（mod+config+world 一起推），无需单独 jar 参数（或 jar 参数与 zip 内 mods/ 合并）。

### 2.3 上传流程

```
上传（选择平台 tab）
├── 方式 A：仅 jar（插件/mod）
├── 方式 B：jar + 内容包 zip（选择 单独配置 / 完全配置）
└── 方式 C：仅内容包 zip（纯配置/整包，无主 jar）
```

上传时校验：
- jar：描述符解析（fabric.mod.json / mods.toml(forge/neoforge) / plugin.yml(spigot/paper) / velocity-plugin.json / bungee.yml），得到 id/name/version/authors/依赖
- 内容包 zip：解压校验（拒绝路径逃逸 `..`/绝对路径/符号链接，Zip Slip 防护），记录目录树快照（顶层结构 + 文件数/大小 + SHA256）

### 2.4 部署

- **目标实例**：按平台过滤（fabric/forge/neoforge→mods 相关，spigot/paper→plugins，velocity/bungee→plugins）
- **单独配置**：内容包解压到实例工作目录（相对结构覆盖），jar 单独部署到 ArtifactDirectory
- **完全配置**：整包解压到实例工作目录——**覆盖策略需谨慎**（含 world 时防误覆盖）：
  - 方案：部署前对目标目录做**快照备份**（或对将要被覆盖的路径备份）；部署为"覆盖同名、保留额外"（与 config-sync 语义一致），可配置"全量替换"选项（高风险，需二次确认）
  - 完全配置常配合镜像组（master image）使用，也可推送到 standalone 实例
- **与 config-sync 关系**：内容包部署 = 一次性推送；镜像组 config-sync = 持续同步；两者共存

### 2.5 前端「仓库」页

- 7 个平台 tab（fabric/forge/neoforge/spigot/paper/velocity/bungee）
- 列表：图标/名称/平台/版本/作者/内容包标记（单独/完全）
- 详情：依赖、内容包结构预览（zip 顶层目录树）、配置类型
- 上传对话框：平台固定 → jar + 可选内容包 + 配置类型选择
- 部署：目标实例选择（按平台过滤）+ 部署类型（jar/单独配置/完全配置）+ 高风险确认（完全配置覆盖 world 时）

### 2.6 内容包管理（删除 / 编辑 / 添加同种配置）

- **删除**：
  - 删除单个内容包（config/full 快照及其存储）
  - 删除制品版本（jar + 其内容包）
  - 删除整个仓库条目（插件/模组）
  - 删除需二次确认与审计；已部署目标记录保留（不可变审计），删除前提示影响
- **编辑 / 添加同种配置**：
  - 内容包**版本化**（类似 jar artifactID 的 contentID）：同一制品下可有多版本内容包，标记 current
  - **编辑**：对内容包重新上传 zip（新建版本并设为 current，或替换——按版本化设计）
  - **添加同种配置**：同一制品下追加同类型（config 或 full）内容包版本
  - 前端：详情提供「编辑配置」「添加同种配置」入口与内容包版本列表（可切换 current）

## 三、关键技术改动点（实施范围）

| 模块 | 改动 |
|---|---|
| **panel/internal/plugins** | `repositoryTypes` 扩至 7（+neoforge/paper）；`ValidPluginType`/`PluginTypeForPlatform` 扩展；Manifest 增加内容包快照（`Content{Type: config\|full, Tree, SHA256}`）；`BuildContentBundle`（通用结构打包，替代硬编码 config/）；上传支持纯内容包 |
| **panel/internal/plugins/descriptor.go** | 新增 neoforge 描述符（mods.toml，与 forge 同解析但标记 neoforge）；paper 描述符（plugin.yml，与 spigot 同源但标记 paper） |
| **daemon/internal/plugins/operations.go** | 新增 `DeployContent`（通用内容包 → 工作目录，相对结构覆盖）；`DeployConfig` 移除"mod 拒绝"（改为通用内容包）；完全配置备份/覆盖策略；路径逃逸校验复用 |
| **daemon/internal/model/server.go** | 平台枚举 +neoforge/paper；`PluginTypeForPlatform`/`IsModPlatform`/`ArtifactDirectory` 扩展（neoforge→mods，paper→plugins） |
| **panel/internal/api** | 上传/部署接口扩展（内容包字段、配置类型）；纯内容包上传 |
| **frontend** | PluginsView → 「仓库」；7 平台 tabs；上传对话框（内容包+类型）；内容包结构预览；完全配置部署确认 |

## 四、待确认决策点

1. **paper 独立性**：paper 作为独立平台标识（描述符标 paper），还是仅 spigot 的一个筛选标签？（建议：独立平台，部署目录仍 plugins/）
2. **完全配置的覆盖策略**：
   - A. 覆盖同名 + 保留额外（与 config-sync 一致，安全）——**推荐**
   - B. 全量替换工作目录（旧内容删除）——高风险，仅手动确认
3. **内容包 zip 顶层结构约定**：
   - 单独配置：zip 顶层含 `config/`（+ 其他按结构映射）
   - 完全配置：zip 顶层即服务端目录（`mods/`、`config/`、`world/`、`plugins/`…）
   - 是否需要"zip 内套一层服务端名目录"的自动剥离？（建议：按"zip 顶层即工作目录"约定，不自动剥离，文档说明）
4. **neoforge 的 mods.toml 解析**：与 forge 共用一个解析器、仅平台标记不同？（建议是）
5. **旧数据兼容**：现有 5 平台的插件仓库数据保留（不迁移），新平台新增目录；paper 制品默认沿用 spigot 目录还是新开 paper 目录？（建议：新开 paper 目录，避免与既有 spigot 制品混淆）

## 五、实施阶段建议

| 阶段 | 内容 | 验收 |
